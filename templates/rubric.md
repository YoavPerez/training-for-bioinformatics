# Evaluation rubric

Used for the module 4 checkpoint, the module 8 mini-project, and the applied project.

| Criterion | What good looks like | Score (1–4) | Notes |
| --- | --- | --- | --- |
| Correctness | Results reproduce from a commit and config | | |
| Evaluation rigor | Distributions, baselines, ablations, honest failure cases | | |
| Code quality | Tested, reviewed, readable, follows conventions | | |
| Communication | Clear report; can defend each design choice | | |
| Independence | Scopes work, asks for help at the right time | | |

Score guide: 1 = not yet, 2 = partially, 3 = meets expectations, 4 = exceeds.

## Level descriptors

| Criterion | 2 = partially | 3 = meets expectations |
| --- | --- | --- |
| Correctness | Numbers reproduce only with help, or with settings missing from the report | Every number reproduces from the stated commit, flags, drive and seed |
| Evaluation rigor | Single numbers, or no baseline; failure cases missing | Distributions or CIs, a baseline and at least one ablation; failure cases shown |
| Code quality | Works, but tests are missing or review comments are still open | Tested, reviewed, CI and lint green, follows `CONVENTIONS.md` |
| Communication | The report needs verbal explanation, or some design choices cannot be defended | A reader follows question → method → result without asking; every design choice is defended |
| Independence | The mentor scoped the work or unblocked most steps | Scoped and time-boxed own work; asked for help after ~2 hours stuck, with what was tried |

## Pass rule (module 8 report for the exit sign-off, and the applied project)
No criterion at 1, and Correctness and Evaluation rigor at 3 or more. At the module 4 checkpoint the scores set the plan for modules 5–8 and are not a pass/fail decision.
